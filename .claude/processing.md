# Processing — Rules

> Scope: `/src/processing` (target `kentos_processing`), the Araçlar panel half of `/src/app`, `/docs/islem`  |  Depends on: `kentos_core`, `kentos_command`, `kentos_io` (for GDAL/GEOS-backed tools); never the reverse (CLAUDE.md 3.2)  |  Source: kentoscad.md §2.1, §2.4, §5.1, §9, §10.4, §13

A processing tool is work applied to many objects at once — label every edge, number every corner, buffer, simplify, dissolve. QGIS calls the family Processing; here it lives inside Article 1: **a tool is a command**. What the module adds is shape: which geometry classes a tool takes, a scope (selection, viewport, project), a worker thread with a progress figure and a stop, and an output layer.

## Hard Rules

R1. Every tool MUST derive from `processing::ProcessingTool` (`tool.hpp`), be declared once with `KENTOS_PROCESSING_TOOL`, and be listed once in `registry.cpp`. That list is the ONLY source of the generated commands, the panel's tree, the Analiz menu and the docs reference (CLAUDE.md 5.10). A tool that exists anywhere else does not exist.
R2. A tool's `ToolSpec` MUST state: a stable id under the `islem.` namespace, names in `.claude/command.md` R7 order (Turkish primary, ASCII-folded, English, abbreviation), a Turkish title and one-sentence summary, its tree group, its `icon` by NAME (`cetvel`, `koordinat`, `yazi`, `alan`, `cizgi`, `nokta`, `sigma`, `islev` — the module is Qt-free and never names a glyph; the panel maps the name), the `Applies` classes it takes, its parameters, and its `OutputShape`. `ToolSpec::to_command_spec()` is the one translation into a `CommandSpec`; nothing hand-writes one for a tool.
R3. The four SHARED parameters are fixed and come first: `nesneler` (keys), `kapsam` (`secili` / `gorunum` / `proje`), `pencere` (two corners for `gorunum`; at the command line two `pencere=` values), `katman` (the output layer, created when missing). A tool's own parameters follow. A tool MUST NOT redeclare or reinterpret them.
R4. A tool NEVER sees the `Document`. It is handed a `ToolInput` — a snapshot of the objects in scope copied on the bus thread — and writes a `ToolOutput` that shares nothing with the document. `ProcessingTool::run` MUST be reentrant and touch nothing but its arguments: it may run on a worker thread while the GUI keeps painting.
R4a. A tool that needs the HAND — which edge, where to — declares an interactive phase by overriding `ProcessingTool::interact(Context&, ToolInput&)`. It runs on the bus thread after the scope is resolved and before the worker, may `co_await ctx.point(...)`, and writes what it learns into `input.args` under the tool's own declared parameters; it MUST NOT touch the document, echo, or journal (the runner does). Everything the hand decided is therefore recorded, and a replay needs no hand (R8). The ghost it shows is a `RubberShape` the canvas draws from a payload the tool encodes (`core/area_edit.hpp` is the pattern: request in, ghost out, deterministic).
R5. The runner (`registry.cpp`, `run_tool`) is the ONLY code that reads the scope, asks for objects when the selection is empty (`want_objects`), applies defaults and validates choices and ranges, hosts the job (`command.md` R8a), writes the output through the command's one transaction, and records the journal. A tool MUST NOT echo, prompt, mutate, or journal.
R6. Objects in scope that a tool does not apply to MUST be skipped AND counted in the transcript ("N nesne bu araca uygun olmadığı için atlandı"). Silent loss is forbidden, exactly as in io.md P11.
R7. `run` MUST check `Progress::cancelled()` at least once per input object and return `processing::cancelled()` when set, and MUST report `Progress::at(done, total)` so the status strip shows a figure. A stopped run writes NOTHING: the runner never reaches the transaction (CLAUDE.md 1.6).
R8. The journal records the RESOLVED objects (`nesneler` as keys) and every parameter with its default applied — never the scope word or the window — so a replay acts on the same objects with the same values whatever the selection or view is then (model.md R43). The equality proof of `test.md` R3 applies: command line and script MUST give one document and one journal; `tests/unit/test_processing.cpp` holds it.
R9. Output objects are ORDINARY objects of existing kinds (captions are `core.polyline` baselines with text, lines and faces are polylines), on the output layer, in one transaction and one undo step. A tool MUST NOT invent a kind to carry its result; a result that needs a new kind is a model change (model.md). A tool that CHANGES its inputs declares `OutputShape::InPlace` and returns `ToolOutput::replacements` — new rings for the same keys; the runner writes them with `set_geometry`, so identity, attributes and captions stay (model.md R4) and the command reads as a Modify command.
R10. Paper-sized figures (a text height, a gap) MUST default from the plan scale (`core.plan.olcek`) as the dimension style does: 2,5 mm of paper at 1/1000 is 2 500 mm of ground. A tool MUST accept an explicit ground value in millimetres and MUST NOT hard-code a ground size.
R11. Lengths and figures a tool writes MUST come from the core formatters (`core::format_dimension_length`, `core::dimension_baseline`) with the user's unit, precision and decimal separator, so a caption written by a tool reads exactly as a dimension does.
R12. A tool that leans on a library (GDAL, GEOS, Clipper2, CGAL) MUST reach it through `/src/io` or `/src/core` wrappers, keep the library's headers inside its own `.cpp`, and obey CLAUDE.md 2.7/5.16 (use the mature library, never reimplement it) and 5.12 (pinned). GRASS is not linked; a GRASS-shaped tool is a KentOSCad tool that happens to compute the same thing.
R13. The Araçlar panel (`app/tools_panel.hpp`) is a CLIENT: it composes a command line from its fields and sends it through `Controller::runLine`, shows that exact line on the card, and does nothing the line does not do. Its tree, chips and fields are generated from `processing_tools()`; a hand-written row is a defect. The card is ONE widget (`ToolCard`) shown either inside the panel or in its own `DialogFrame` window, chosen by the App setting `core.islem.pencere` (`TERCİH araç_penceresi`); the two never differ in what they send.
R14. Every tool ships, in the same change: its `docs/komutlar/<slug>.md` page with the eight sections (docs.md R7), a row in `docs/islem/README.md`, a line in `CHANGELOG.md`, a regenerated `docs/komutlar/referans.md`, and tests: the spec (names, applies, parameter order), the result on each class it applies to, the scope, a stop leaving nothing, and undo.
R15. `kentos_processing` MUST compile Qt-free (Article 3.4); `scripts/ci-gate-layering.sh` refuses an include of render, script, ai, domain or app from it. Every mutation goes through `Transaction` (`scripts/ci-gate-command-mutation.sh` checks `/src/processing`).

## Absolute Prohibitions

P1. NEVER let a tool touch the `Document`, the `Bus`, the selection or the settings — not from `run`, not from a helper. The snapshot is the contract.
P2. NEVER run `ProcessingTool::run` on the GUI thread when the session can host a job, and NEVER write to the document from the worker. The runner's three phases (`registry.cpp`) are the only shape.
P3. NEVER apply a partial result. A stop, a failure or a refused object rolls the run back whole (CLAUDE.md 1.6).
P4. NEVER add a tool that is reachable only from the panel (CLAUDE.md 5.15). The generated command IS the tool; the panel is a convenience.
P5. NEVER hand-maintain the panel's tree, the Analiz menu or a docs table of tools by hand where it can be generated; `docs/islem/README.md`'s table is the one pointer table the docs index convention allows, and it is checked by the docs gate through the pages it links.

## Adding a tool

1. `src/processing/src/tools/<name>.cpp`: a `final` class deriving `ProcessingTool`; a `static const ToolSpec` built with `ToolParam::choice/integer/text/point/boolean`; `run` over `input.entities`, checking `progress.cancelled()` and calling `progress.at()`; `KENTOS_PROCESSING_TOOL(<name>)` returning a function-local static.
2. `registry.cpp`: the forward declaration and one line in `all_tools()`. `CMakeLists.txt`: the source.
3. The page, the row, the changelog line, `make reference`, the tests (R14).
4. The hand probe (`KENTOS_HAND_PROBE`) selects every tool by id and prints the line the panel composes; a new tool appears there by being in the list.
